## LLMs / GenAI

### 1. How does KV caching improve LLM inference speed?
During autoregressive decoding, every new token must attend over every prior token, so without caching the model would recompute the key and value projections for the entire prefix at each step — turning per-step work from O(n) into O(n²) FLOPs. The KV cache stores per-layer K and V tensors once they are computed; the prefill phase fills the cache for the whole prompt in a single compute-bound pass, while each decode step appends one new K/V row and reads the entire cache (memory-bandwidth bound). Cache size scales roughly as `2 · n_layers · n_kv_heads · d_head · seq_len · batch · bytes_per_elem`, which for a 70B model at 128K context dominates GPU memory and drives the need for GQA, FP8 KV, and eviction. vLLM's PagedAttention treats this cache like virtual memory: it is broken into fixed-size blocks (typically 16 tokens) allocated on demand, eliminating the 60–80% internal fragmentation that contiguous pre-allocation suffered and enabling prefix sharing across requests.

**Sources**: [KV Cache Memory Calculation — Lyceum Technology](https://lyceum.technology/magazine/kv-cache-memory-calculation-llm/) · [PagedAttention & vLLM — Data Science Dojo](https://datasciencedojo.com/blog/understanding-paged-attention/)

### 2. Explain Mixture of Experts (MoE) architecture
An MoE layer replaces a dense FFN with N parallel "expert" FFNs plus a small router (a linear gate over the token's hidden state) that picks the top-k experts to run per token; only those k experts contribute, so compute scales with active rather than total params. The decoupling lets total capacity grow far faster than per-token FLOPs: Mixtral 8x7B has ~47B total parameters but routes top-2 of 8 experts, doing the work of roughly a 13B dense model; DeepSeek-V3 has 671B total but only ~37B active per token across 256 routed experts (8 active) plus a shared expert, and recent open-weight MoEs (GPT-OSS, Qwen MoE, GLM-class) follow the same shape. Training-time challenges are load balancing (auxiliary loss or DeepSeek-V3's auxiliary-loss-free bias-update trick) and routing collapse; serving-time challenges are expert parallelism — experts are sharded across GPUs and the router triggers all-to-all communication so each token reaches its chosen experts. The win is roughly 10× lower active FLOPs at equal quality, which NVIDIA attributes much of the recent frontier cost-per-token drop to.

**Sources**: [MoE LLMs — Cameron R. Wolfe](https://cameronrwolfe.substack.com/p/moe-llms) · [Mixture of Experts on NVIDIA Blackwell — NVIDIA Blog](https://blogs.nvidia.com/blog/mixture-of-experts-frontier-models/)

### 3. What happens internally during token generation?
Generation runs in two phases with very different hardware profiles. In **prefill**, the entire prompt is pushed through every transformer layer in one parallel matmul pass — compute-bound, high GPU utilization — and the resulting K/V tensors are written into the cache. In **decode**, the model loops one token at a time: project the last token to Q, attend over the cached K/V, run the FFN/MoE, produce logits, sample, append the new token's K/V to the cache, repeat — this is memory-bandwidth-bound because almost no math is done per byte of weights loaded. Sampling converts logits to a token: greedy picks argmax; temperature divides logits by T before softmax (T<1 sharpens, T>1 flattens); top-k restricts the candidate pool to the k highest-prob tokens; top-p (nucleus) keeps the smallest set whose cumulative probability ≥ p, adapting pool size to model confidence. Generation halts on an EOS/stop token, a max-tokens limit, or a user-defined stop string; the vLLM/llama.cpp community has largely converged on temperature + min-p as the cleanest two-knob setup.

**Sources**: [HuggingFace LLM Course — Text Generation Inference](https://huggingface.co/learn/llm-course/en/chapter1/8) · [LLM Temperature, Top-P, Top-K Explained](https://machinelearningplus.com/gen-ai/llm-temperature-top-p-top-k-explained/)

### 4. How would you serve an LLM to millions of users?
You stop thinking in "batch one request" and start thinking in token-level scheduling. **Continuous (in-flight) batching** — pioneered by Orca and now standard in vLLM, TGI v3, TensorRT-LLM, and SGLang — admits new requests into the running batch at each decode step instead of waiting for the slowest to finish, scaling throughput nearly linearly with concurrency. Memory is managed via **PagedAttention** so unrelated requests share GPU memory without fragmentation, and prefix caching lets system prompts / chat history reuse cached K/V. For models too large for one GPU you combine **tensor parallelism** (shard matmuls across GPUs within a node, NVLink-bound) with **pipeline parallelism** (split layers across nodes) and, for MoE, **expert parallelism**. On top sit an autoscaler (separate prefill vs decode pools is increasingly common — "disaggregated serving"), a request scheduler that respects SLOs, speculative decoding, FP8/INT4 weights, and a gateway that handles auth, rate limiting, and routing. Stripe reported a 73% inference-cost reduction migrating to vLLM, serving 50M daily calls on one-third the prior GPU fleet.

**Sources**: [vLLM vs TensorRT-LLM vs TGI vs LMDeploy — MarkTechPost](https://www.marktechpost.com/2025/11/19/vllm-vs-tensorrt-llm-vs-hf-tgi-vs-lmdeploy-a-deep-technical-comparison-for-production-llm-inference/) · [vLLM Continuous Batching for Long Contexts](https://www.johal.in/vllm-continuous-batching-high-throughput-serving-for-long-contexts-2025/)

### 5. Tradeoffs between fine-tuning and RAG
RAG wins on **freshness, attribution, and cost of change**: knowledge lives in a vector store you can update in seconds, the model can cite sources, and per-query cost is roughly LLM tokens + a retrieval call (typically well under $5 per 1k queries). Fine-tuning wins on **behavior shaping**: tone, output format, domain-specific reasoning patterns, latency (no retrieval hop), and cases where the task is "learn this skill" rather than "look this fact up." Full fine-tuning runs $5k–$50k+ per pass and you redo it every time the data drifts; LoRA/QLoRA collapses that to ~$100–$1k by training small low-rank adapters (typically r=8–64) on top of frozen weights, which is why ~90% of production fine-tunes in 2026 are LoRA. The honest decision rule: if the failure mode is "doesn't know X," RAG; if it's "doesn't sound/behave like X," fine-tune; if it's both — and most enterprise systems are — use a **hybrid** (LoRA for voice/format, RAG for facts), which one cross-domain study found delivered ~22% higher accuracy at ~40% lower compute than either alone. RAG also has lower hallucination risk *when retrieval is grounded and cited*, but adds a new failure mode (bad retrieval → confident wrong answer) that fine-tuning doesn't have.

**Sources**: [LoRA vs Fine-tuning vs RAG — BuilderWorld](https://builderworld.io/en/learn/lora-vs-fine-tuning-vs-rag) · [RAG vs Fine-Tuning — Heavybit](https://www.heavybit.com/library/article/rag-vs-fine-tuning)

### 6. Attention complexity — why it becomes expensive
Standard softmax attention computes an n×n score matrix QKᵀ then softmax(·)V, costing **O(n²·d) FLOPs and O(n²) memory** for sequence length n and head dim d — at 100k tokens that's a 10-billion-entry matrix per head per layer. The real bottleneck on modern GPUs isn't FLOPs but HBM traffic: writing/reading the n×n matrix to high-bandwidth memory dominates wall time. **FlashAttention** restructures the kernel to tile Q, K, V into SRAM blocks and fuse softmax + matmul so the n×n matrix is never materialized in HBM — it requires roughly N²d²/M I/O ops (M = SRAM size), giving large speedups while computing **exact** attention; FLOPs are unchanged. **FlashAttention-3** adds asynchrony (overlap GEMM and softmax) and FP8 on Hopper, hitting ~75% of H100 peak vs FA-2's ~35%. To break the asymptotic wall you change the math, not the I/O: **sliding-window attention** (Mistral, Longformer) restricts each token to a window of w neighbors → O(n·w·d), and **linear attention** variants (Performer, RWKV, Mamba-style SSMs) replace softmax with a kernel that allows associative recomputation in O(n·d²), trading exactness for true linear scaling.

**Sources**: [FlashAttention-3 paper (arXiv)](https://arxiv.org/pdf/2407.08608) · [I/O Complexity of Attention (arXiv)](https://arxiv.org/pdf/2402.07443)

### 7. What is speculative decoding?
Speculative decoding splits each decode step into **draft** and **verify**: a cheap drafter proposes K future tokens, and the expensive target model runs *one* forward pass that scores all K positions in parallel, accepting the longest prefix whose sampled distributions match (under a rejection-sampling rule that preserves the target's output distribution exactly — outputs are mathematically identical to standard sampling). Speedup ≈ accepted-tokens-per-step ÷ (1 + drafter cost ratio); typical production systems land in the **~2–3× wall-clock range** on chat workloads. Variants differ in where the drafter comes from: a separate small model (vanilla speculative decoding from DeepMind/Google), **Medusa** adds extra prediction heads on top of the target so no separate model is needed, **EAGLE** / EAGLE-3 train a single transformer decoder layer that drafts in the target's *feature* space (achieving 1.5–2.1× over Medusa/Lookahead), and **n-gram / lookahead / PARD** methods retrieve drafts from prior generation or a suffix automaton — zero training cost but lower acceptance. A high acceptance rate doesn't guarantee throughput: if the drafter is too heavy or the verification batch swells, you can lose the win, so engines tune draft length adaptively.

**Sources**: [EAGLE: Speculative Sampling (arXiv)](https://arxiv.org/pdf/2401.15077) · [Speculative Decoding Implementations Overview](https://www.digitado.com.br/speculative-decoding-implementations-eagle-3-medusa-1-pard-draft-models-n-gram-and-suffix-decoding-from-scratch-p/)

### 8. How would you detect hallucinations automatically?
There is no single method — you stack signals. **SelfCheckGPT** samples the same prompt N times at non-zero temperature and measures consistency across samples (via BERTScore, n-gram, NLI, or LLM-as-judge); facts that the model "knows" stay stable while hallucinations drift, so high inter-sample disagreement flags suspicious spans. **Semantic entropy** (Farquhar et al., Nature 2024) is the more principled version: cluster samples by *meaning* (using bidirectional NLI entailment) and compute entropy over semantic clusters rather than tokens — high semantic entropy correlates strongly with hallucination and is the current SOTA black-box signal. **Retrieval-grounding checks** verify each generated claim against retrieved documents using NLI ("does passage X entail claim Y?") — this is how RAG systems like RefChecker work and is the basis of the SemEval-2025 Mu-SHROOM task. **Citation verification** parses cited spans and confirms they exist and support the claim. **LLM-as-judge** with a strong critic model is cheap to deploy but biased; recent work shows other detectors can drop up to 45.9% AUROC under human-aligned judge evaluation, so judges should be ensembled, not trusted solo. Production stacks combine: low-temperature regeneration → semantic-entropy gate → NLI against retrieved evidence → judge for residuals.

**Sources**: [Detecting Hallucinations Using Semantic Entropy — Nature](https://www.nature.com/articles/s41586-024-07421-0) · [How to Detect Hallucinations — Maxim AI](https://www.getmaxim.ai/articles/how-to-detect-hallucinations-in-your-llm-applications/)

### 9. Model quantization — what & why it matters
Quantization replaces FP16/BF16 weights (and sometimes activations) with low-precision integers or narrow floats, shrinking memory ~2–4× and — because LLM decode is memory-bandwidth bound — proportionally speeding up inference. **Weight-only INT4 (W4A16)** keeps activations in FP16 and is the most cost-efficient choice for low-batch / synchronous serving; **GPTQ** does layer-wise error minimization using second-order (Hessian) info, **AWQ** identifies the ~1% of salient weight channels via activation statistics and scales them up before uniform quantization, preserving accuracy better in most benchmarks. **Activation quantization (W8A8)** unlocks INT8/FP8 tensor cores and dominates in asynchronous continuous batching; the challenge is activation outliers, which **SmoothQuant** handles by migrating quantization difficulty from activations to weights via a per-channel scaling factor (1.56× speedup, 2× memory cut, near-zero accuracy loss on OPT/Llama/Mixtral). The 2025 accuracy picture: **FP8 is effectively lossless** at every scale, well-tuned INT8 loses 1–3%, and INT4 weight-only now rivals 8-bit on many benchmarks — which is why FP8 is becoming the data-center default and FP4 (Blackwell) is the next frontier.

**Sources**: [Optimizing LLMs with Post-Training Quantization — NVIDIA Blog](https://developer.nvidia.com/blog/optimizing-llms-for-performance-and-accuracy-with-post-training-quantization/) · [SmoothQuant paper (arXiv)](https://arxiv.org/pdf/2211.10438)

### 10. How embedding models differ from generative models
Generative LLMs are decoder-only causal models trained with next-token prediction; embedding models map a piece of text to a single fixed-length vector trained so semantically similar texts land close in cosine space. Historically embedders were **encoder-only** (BERT, E5, BGE) with bidirectional attention and a pooling step (CLS-token or mean pooling over last-hidden-states), trained with **contrastive learning** (InfoNCE / multiple-negatives ranking) on (query, positive, hard-negative) triples — often distilled from larger teachers. The dominant 2024–2026 trend reverses this: take a **decoder LLM**, remove the causal mask (or use last-token pooling), and contrastively fine-tune it — **NV-Embed** (Mistral-7B base, latent-attention pooling, two-stage instruction-tuned contrastive training) topped MTEB at 69.32, and **E5-Mistral** and LLM2Vec follow the same recipe. The benchmark of record is **MTEB**, covering ~56 tasks across retrieval, classification, clustering, STS, and reranking; embedders are evaluated on these, not on perplexity. Practical implication: embedding models are typically 100×–1000× cheaper per call than generators and you can serve millions of vectors per second, but they only produce similarity scores, not text — so RAG always pairs a small fast embedder for retrieval with a large generator for synthesis.

**Sources**: [NV-Embed paper (arXiv)](https://arxiv.org/pdf/2405.17428) · [Best Embedding Models of 2025 — Future AGI](https://futureagi.com/blog/best-embedding-models-2025/)

## Classical Machine Learning

### 1. Why does Batch Normalization improve training stability?
The original 2015 Ioffe & Szegedy paper claimed BatchNorm works by reducing **internal covariate shift** — the changing distribution of layer inputs as upstream weights update — by normalizing each mini-batch activation to zero mean and unit variance, then applying learned scale γ and shift β. Santurkar et al. (NeurIPS 2018) decisively challenged this: they injected noise *after* BatchNorm layers to deliberately reintroduce distributional shift, and the networks still trained faster than un-normalized baselines, showing covariate shift had little to do with the benefit. Their alternative explanation is that BatchNorm **smooths the optimization landscape**, provably reducing the Lipschitz constants of the loss and its gradients (β-smoothness). The practical consequence is that gradients become more predictive across step sizes, so larger learning rates are safe and convergence is faster. Both views appear in interview answers; the modern technically-correct one is the loss-landscape view.

**Sources**: [How Does Batch Normalization Help Optimization? (Santurkar et al., arXiv:1805.11604)](https://arxiv.org/abs/1805.11604) · [Batch Normalization vs Internal Covariate Shift (ML Journey)](https://mljourney.com/batch-normalization-vs-internal-covariate-shift/)

### 2. Explain vanishing and exploding gradients
By the chain rule, the gradient at layer ℓ is a product of Jacobians: ∂L/∂Wℓ ∝ ∏ Wₖ · σ′(zₖ). If singular values are <1 (or activations like sigmoid/tanh saturate so σ′→0), the product **shrinks exponentially** → vanishing gradients; if singular values are >1, it **explodes**. Mitigations attack each factor: **Xavier/Glorot init** sets Var(W)=1/n_in (good for tanh/sigmoid) and **He init** sets Var(W)=2/n_in (good for ReLU since it zeros half the pre-activations), keeping signal variance ≈1 across layers. **Gradient clipping** caps ||g|| ≤ τ (or rescales g·τ/||g||) to bound explosions, standard for RNN training. **Residual connections** (y = x + F(x)) add an identity Jacobian so ∂y/∂x = I + ∂F/∂x, giving a "gradient highway" that prevents the product from collapsing. **LSTM gating** routes long-range gradients through the cell state c_t = f_t ⊙ c_{t-1} + i_t ⊙ g_t — when the forget gate f≈1 the gradient flows linearly through time, sidestepping the vanishing-product problem in vanilla RNNs.

**Sources**: [Vanishing and Exploding Gradients Problems in Deep Learning (GeeksforGeeks)](https://www.geeksforgeeks.org/deep-learning/vanishing-and-exploding-gradients-problems-in-deep-learning/) · [Exploring Vanishing and Exploding Gradients in Neural Networks (Analytics Vidhya)](https://www.analyticsvidhya.com/blog/2024/04/exploring-vanishing-and-exploding-gradients-in-neural-networks/)

### 3. Difference between L1 and L2 regularization mathematically
L1 (Lasso) adds λ·∑|wᵢ| to the loss, L2 (Ridge) adds λ·∑wᵢ². The gradient of L2 is 2λw — a smooth **shrinkage** proportional to the weight's magnitude, never driving it exactly to zero. L1's derivative is the **subgradient** ∂|w| = sign(w) for w≠0 and [-1,1] at w=0; the optimality condition |∂Loss/∂wᵢ| ≤ λ can be satisfied at exactly wᵢ=0 for a whole range of gradients, which is why L1 produces **sparse solutions** (geometrically: L1's diamond constraint region has corners on the axes). The **Bayesian view**: MAP estimation with a Gaussian prior w ∼ N(0, σ²) yields L2 (the negative log-prior is quadratic in w), while a Laplace prior w ∼ Laplace(0, b) — sharply peaked at zero — yields L1. The peak's mass at zero is exactly why Laplace/L1 zeros out weights while Gaussian/L2 only shrinks them.

(Dataversity)](https://www.dataversity.net/articles/regularization-for-logistic-regression-l1-l2-gauss-or-laplace/) · [L1 vs L2 Regularization: Intuition, Geometry, and Bayesian View](https://medium.com/@iambeingferoz/l1-vs-l2-regularization-intuition-geometry-and-bayesian-view-da18a2b74de1)

### 4. Why do ensemble methods improve performance?
Through the bias-variance lens, an ensemble's prediction is an average f̄ = (1/M)∑fₘ. If learners are **independent** with variance σ², averaging gives Var(f̄) = σ²/M — pure variance reduction with no bias change. In reality learners are correlated (ρ > 0), and the variance becomes ρσ² + (1-ρ)σ²/M, so the floor is ρσ² no matter how many learners you add; **decorrelation is therefore the lever**. **Bagging** decorrelates by bootstrap-sampling training data; Random Forests add column subsampling at each split to drive ρ further down — this is why they primarily reduce *variance*. **Boosting** (AdaBoost, GBM, XGBoost) fits learners sequentially to the residuals/mistakes of prior ones, so each new weak learner targets the regions the ensemble still mispredicts — this primarily reduces *bias*. The Condorcet-jury intuition: if each independent learner has error rate p < 0.5, majority vote of M learners has error → 0 as M → ∞; correlation among learners is what slows that convergence in practice.

**Sources**: [Bagging vs Boosting: A Deep Dive into Ensemble Learning](https://medium.com/data-science-collective/bagging-vs-boosting-a-deep-dive-into-ensemble-learning-for-tree-based-models-b3a061da3e62) · [Ensemble Learning: Bagging & Boosting (Towards Data Science)](https://towardsdatascience.com/ensemble-learning-bagging-boosting-3098079e5422/)

### 5. ROC-AUC limitations on imbalanced datasets
ROC plots TPR vs FPR; both are computed **within a class** (TPR = TP/P, FPR = FP/N), so neither sees the prevalence π = P/(P+N). This makes ROC-AUC **invariant to class skew**: a classifier with AUC = 0.95 on a 50/50 split keeps the same AUC if you down-sample negatives to make it 1/99, even though precision collapses. Saito & Rehmsmeier (2015, PLOS ONE) showed this directly: when positives are rare, the false-positive rate denominator (N) is huge, so a flood of false positives barely budges FPR, and ROC-AUC stays optimistic. **Precision** = TP/(TP+FP) does include both classes and degrades immediately as FPs grow relative to scarce TPs, so the **PR curve and PR-AUC** reflect real-world utility for rare-positive tasks (fraud, disease screening, retrieval). Rule of thumb: if base rate < ~10%, report PR-AUC alongside ROC-AUC and use average precision as the headline metric.

**Sources**: [Saito & Rehmsmeier 2015, PLOS ONE](https://journals.plos.org/plosone/article?id=10.1371%2Fjournal.pone.0118432) · [Precision-Recall Plot Is More Informative on Imbalanced Datasets (PMC)](https://pmc.ncbi.nlm.nih.gov/articles/PMC4349800/)

### 6. What is covariate shift?
Covariate shift is the dataset-shift regime where **P_train(X) ≠ P_test(X) but P(Y|X) is invariant** — the input distribution moves while the underlying input→output mapping is unchanged. Contrast with **concept drift**, where P(Y|X) itself changes (the world's labeling function has shifted: e.g., fraud patterns adapting to a defense). The standard correction is **importance weighting**: reweight each training example by w(x) = P_test(x)/P_train(x), the density ratio (Radon-Nikodym derivative), and minimize the weighted empirical risk; this gives an unbiased estimator of test-distribution risk. Density-ratio estimation methods (KLIEP, uLSIF, discriminative class-probability ratios) estimate w(x) directly to avoid two error-prone density estimates. The name **"internal covariate shift"** in BatchNorm was Ioffe & Szegedy's analogy: each layer's input distribution shifts during training as upstream weights update, mirroring the train/test covariate-shift problem one layer deep — though Santurkar et al. (Q1) showed this isn't actually why BatchNorm works.

**Sources**: [Covariate Drift (Insightful Data Lab)](https://insightful-data-lab.com/2025/08/19/covariate-drift-a-k-a-covariate-shift/) · [Batch Normalization — Covariate Shift (BayernCollab)](https://collab.dvb.bayern/spaces/TUMlfdv/pages/69119920/Batch+Normalization)

### 7. Why does PCA maximize variance?
PCA seeks unit-norm directions w that maximize the projected variance Var(Xw) = wᵀΣw, where Σ is the sample covariance. Set up the Lagrangian L(w, λ) = wᵀΣw − λ(wᵀw − 1); taking ∂L/∂w = 0 gives **Σw = λw**, the eigenvalue equation. So stationary points are eigenvectors of Σ, and at any such w the objective equals wᵀΣw = wᵀ(λw) = λ — meaning **maximizing variance picks the eigenvector with the largest eigenvalue**, the second largest gives the next PC orthogonal to it, and so on. The dual view: minimizing reconstruction error ∑ ||xᵢ − WWᵀxᵢ||² over orthonormal W is **equivalent** because ||x||² = ||WWᵀx||² + ||x − WWᵀx||² (Pythagoras on orthogonal projection), and ||x||² is fixed, so minimizing reconstruction error = maximizing the projected component. Algebraically the reconstruction error equals the sum of *discarded* eigenvalues, so keeping the top-k eigenvectors minimizes it.

**Sources**: [The Math of Principal Component Analysis (Harvard CS181 notes)](https://onefishy.github.io/ML_notes/the-math-of-principal-component-analysis.html) · [PCA Lecture Notes — Laurenz Wiskott (Stanford-hosted)](http://graphics.stanford.edu/courses/cs233-25-spring/ReferencedPapers/LectureNotes-PCA.pdf)

### 8. Explain bias-variance decomposition
Assume y = f(x) + ε with E[ε] = 0, Var(ε) = σ². For a model f̂ trained on a random dataset, the expected squared error at x is **E[(y − f̂(x))²] = (E[f̂(x)] − f(x))² + Var(f̂(x)) + σ²** = Bias² + Variance + irreducible noise. Derivation: expand (y − f̂)² = ((f − E[f̂]) + (E[f̂] − f̂) + ε)²; cross-terms vanish in expectation because ε is independent and (E[f̂] − f̂) has mean zero. **Bias²** measures systematic error — how far the *average* prediction (over training-set resamples) is from the true f. **Variance** measures sensitivity — how much f̂ wobbles when training data is resampled. **σ²** is the floor; no model can beat it. As model complexity grows, capacity rises so bias falls (the model can fit more shapes) but variance rises (it also fits noise); the optimal complexity minimizes the sum. This is the formal justification for regularization, early stopping, and ensembling.

**Sources**: [Bias–variance tradeoff (Wikipedia)](https://en.wikipedia.org/wiki/Bias%E2%80%93variance_tradeoff) · [Statistical Justifications; the Bias-Variance Decomposition (UC Berkeley CS189 Lec 12)](https://people.eecs.berkeley.edu/~jrs/189s19/lec/12.pdf)

### 9. What is the curse of dimensionality?
As dimensionality d grows, several geometric pathologies kick in simultaneously. **Distance concentration**: for many distributions, (max_i ||xᵢ|| − min_i ||xᵢ||) / min_i ||xᵢ|| → 0 as d → ∞, so all pairwise distances become nearly equal and "nearest neighbor" loses meaning. **Volume-in-shells**: in a d-ball, the fraction of volume within the outer ε-shell is 1 − (1−ε)^d → 1, so essentially all mass lives near the surface, not the interior — uniform samples cluster at the boundary. **Sample complexity** for density estimation or fixed-resolution grid coverage scales as **O(k^d)** (exponential in d): covering each dimension at resolution k requires k^d cells, so a histogram or kernel density estimator needs exponentially many samples to keep average bin counts non-trivial. Practical consequences: **kNN** degrades because all neighbors are equidistant, so weighting/ranking loses signal; **kernel density estimation** suffers slow MSE rates of O(n^(−4/(4+d))); Gaussian assumptions become a near-necessity since nonparametric methods are starved. Mitigations: dimensionality reduction (PCA, autoencoders), feature selection, manifold assumptions, or distance metrics like L1/cosine that concentrate less than L2.

**Sources**: [Interpreting the Curse of Dimensionality from Distance Concentration (arXiv 2401.00422)](https://arxiv.org/html/2401.00422v3) · [Curse of Dimensionality (Emergent Mind)](https://www.emergentmind.com/topics/curse-of-dimensionality)

### 10. How would you debug model drift in production?
Set up **three layers of monitoring** running on rolling windows (e.g., daily/hourly) against frozen training and healthy-serving baselines. **(1) Input drift**: per-feature distribution checks — **PSI** for tabular (PSI < 0.1 stable, 0.1–0.25 minor, > 0.25 major / retrain trigger), **KS test** for continuous features, **chi-square** for categorical; for embeddings/text use Wasserstein or MMD. **(2) Prediction drift**: track the distribution of model outputs (score histograms, predicted-class rates); a stable model on shifting inputs will usually show prediction drift first, before labels arrive. **(3) Performance**: once ground-truth labels land (possibly weeks later for credit/churn), compute live AUC/PR-AUC/loss vs the training baseline; alert on sustained degradation, not single-day spikes. **Root-cause categorization**: if P(X) changed but P(Y|X) holds, it's **covariate shift** (often fixable by importance weighting or a feature pipeline fix); if calibration breaks and label rates have shifted but inputs look stable, it's **concept drift** (requires retraining on new labels). **Retrain triggers**: require drift to persist across N windows with enough sample volume to avoid retraining storms from traffic anomalies; tie automated retraining to a champion-challenger shadow evaluation before promotion, and keep a rollback path. Tools that wire this end-to-end include Evidently, WhyLabs, Arize, and Fiddler.

**Sources**: [Data Drift: Key Detection and Monitoring Techniques in 2026 (Label Your Data)](https://labelyourdata.com/articles/machine-learning/data-drift) · [Model Drift Detection Tutorial 2026 (mlopslab.org)](https://mlopslab.org/model-drift-detection-tutorial-how-to-monitor-ml-models-in-production-2026/)

## Deep Learning

### 1. Why are Transformers better than RNNs for LLMs?
RNNs process tokens strictly sequentially — the hidden state at step *t* depends on step *t-1* — so the number of sequential operations is O(n), bottlenecked by a single core's clock and unable to saturate GPU/TPU parallelism. Transformers have O(1) sequential depth: every token's representation is computed in parallel via batched matrix multiplications (Q, K, V projections followed by softmax(QKᵀ/√d)·V), letting modern hardware ingest an entire document at once. They also give every position a direct edge to every other position, so long-range dependencies traverse one layer instead of *n* recurrent steps that erode signal via vanishing gradients. The honest tradeoff is quadratic memory and compute in sequence length n — naive attention is O(n²) — which is why long-context Transformers need FlashAttention, KV-cache tricks, sliding windows, or linear-attention variants. The field paid that VRAM price because dense linear algebra scales on accelerators in a way recurrence fundamentally cannot.

**Sources**: [Transformer (Wikipedia)](https://en.wikipedia.org/wiki/Transformer_(machine_learning_model)) · [Attention as an RNN (arXiv 2405.13956)](https://arxiv.org/html/2405.13956v2)

### 2. Explain positional encoding
Self-attention is permutation-invariant, so position must be injected explicitly. Vaswani et al. (2017) used fixed sinusoidal encodings PE(pos, 2i) = sin(pos / 10000^(2i/d)), PE(pos, 2i+1) = cos(...), added to token embeddings — letting any offset be a linear function of the original. Learned absolute embeddings (BERT, GPT-2) replace the formula with a trainable table but extrapolate poorly beyond trained lengths. **RoPE** (Su et al. 2021, now dominant in LLaMA, Qwen, Mistral, DeepSeek) rotates each consecutive pair of dimensions in Q and K by an angle mθᵢ where m is the token's position; because rotation matrices satisfy R(m)ᵀR(n) = R(n−m), the dot product qₘ·kₙ becomes a function of *only* the relative distance n−m, giving relative-position awareness with zero added parameters and graceful length extrapolation. **ALiBi** (Press et al. 2022) skips embeddings entirely and just adds a linear bias −m·|i−j| to attention logits, which extrapolates well but is less expressive than RoPE's full rotation.

**Sources**: [Rotary Embeddings: A Relative Revolution (EleutherAI)](https://blog.eleuther.ai/rotary-embeddings/) · [Position Encoding Comparison (Brenndoerfer)](https://mbrenndoerfer.com/writing/position-encoding-comparison-transformers)

### 3. What is masked self-attention?
Masked (causal) self-attention enforces the autoregressive constraint: token *i* may only attend to tokens 1…i, never to future tokens. Implementation is a strictly upper-triangular matrix M with −∞ above the diagonal and 0 elsewhere, added to the raw attention scores: softmax((QKᵀ/√d) + M)·V. The −∞ entries become exactly 0 after softmax, zeroing out forward-looking edges while keeping the rest of the computation a single dense matmul. This is what makes decoder-only models (GPT, LLaMA, Mistral) trainable in parallel via **teacher forcing** — for a length-n sequence, all n next-token predictions are computed in one forward pass on the ground-truth prefix, instead of n sequential rollouts. The same mask is used at both prefill (prompt) and decode time so the model behaves identically in training and generation.

**Sources**: [Decoder Architecture: Causal Masking & Autoregressive Generation (Brenndoerfer)](https://mbrenndoerfer.com/writing/decoder-architecture-causal-masking-autoregressive-transformers) · [StableMask: Refining Causal Masking (arXiv 2402.04779)](https://arxiv.org/pdf/2402.04779)

### 4. Why does attention work so well?
Attention is **dynamic content-based routing**: the weights softmax(QKᵀ/√d) are computed from the data at every forward pass, so each token decides at runtime which other tokens are relevant — unlike convolutions (fixed local receptive field) or RNNs (fixed sequential pipe). Every position has a direct path of depth 1 to every other position, so credit assignment for long-range dependencies doesn't have to fight n layers of vanishing gradient. Mechanistic interpretability has shown that this routing self-organizes into specialized circuits — **induction heads**, for instance, implement in-context pattern completion ("A B … A → B") and ablating them drops in-context learning performance by ~32%, near random. Finally, attention's inductive bias is deliberately weak (any-to-any, no locality assumption), which is what makes it scale: it doesn't impose strong priors that get in the way once you have internet-scale data, so increasing parameters and tokens predictably improves it.

**Sources**: [Mechanistic Interpretability: Induction Heads (Yu)](https://ytcs.github.io/machine-learning/2025/05/25/mechanistic-interpretability-part-7.html) · [When Does Content-Based Routing Work? (arXiv 2603.20997)](https://arxiv.org/pdf/2603.20997)

### 5. Difference between encoder-only and decoder-only models
**Encoder-only** (BERT, RoBERTa, DeBERTa): bidirectional self-attention, pretrained with masked language modeling (MLM) — predict a masked token using both left and right context. Produces rich per-token representations; best for classification, NER, retrieval, sentence embeddings. Cannot generate fluently because no causal structure. **Decoder-only** (GPT-2/3/4, LLaMA, Mistral): causal self-attention, pretrained with next-token prediction. Naturally generative; every pretraining step is also an in-context learning step. **Encoder-decoder** (T5, BART, original Transformer): bidirectional encoder feeds cross-attention into a causal decoder; strong for translation and structured seq2seq. Decoder-only won at scale for three reasons documented by Yi Tay (ex-Google Brain): (a) the pretraining task (next-token) is universal and matches every downstream task by prompting, (b) the architecture is simpler (no cross-attention, one stack), and (c) BERT-style encoders plateaued at ~hundreds of millions of parameters while GPT-3 (175B) showed decoder-only continues to scale predictably for both understanding and generation.

**Sources**: [What happened to BERT & T5? (Yi Tay)](https://www.yitay.net/blog/model-architecture-blogpost-encoders-prefixlm-denoising) · [Understanding Encoder and Decoder LLMs (Sebastian Raschka)](https://magazine.sebastianraschka.com/p/understanding-encoder-and-decoder)

### 6. What are residual connections and why important?
A residual (or skip) connection sets y = x + F(x), where F is the block being learned (He et al. 2015, ResNet). They solve the **degradation problem**: empirically, naively stacking layers made training error *worse* past ~20 layers because optimization, not capacity, was the bottleneck. With the skip, the block only needs to learn the *residual* F(x) = H(x) − x; if the optimal mapping is near identity, F can be driven toward zero, which is much easier than learning identity from scratch. Gradients also get an unobstructed identity path during backprop (∂y/∂x = I + ∂F/∂x), preventing vanishing through depth and enabling 100+ layer CNNs and 96+ layer Transformers. Veit et al. (2016) further showed residual nets behave like an **implicit ensemble** of 2^L paths of varying length, and most useful gradient flows through paths of only 10–34 layers in a 110-layer net — meaning the network never truly trains as "very deep" end-to-end. Residual connections are a strict prerequisite for Transformer depth: every Transformer block is x → x + Attn(LN(x)) → x + FFN(LN(x)).

**Sources**: [Deep Residual Learning for Image Recognition (He et al. 2015)](https://arxiv.org/pdf/1611.01186) · [Residual Networks Behave Like Ensembles (Veit et al. 2016)](https://arxiv.org/abs/1605.06431)

### 7. Explain gradient clipping
Gradient clipping bounds the gradient magnitude before the optimizer step to prevent rare huge updates from blowing up the weights. **Clip-by-norm** (the standard for LLMs) computes the global L2 norm ‖g‖ across *all* parameter gradients concatenated; if ‖g‖ > τ, it rescales g ← g · τ/‖g‖, preserving the gradient's *direction* and only shrinking its magnitude. **Clip-by-value** clamps each component independently to [−c, c], which is simpler but distorts the gradient direction and is considered less principled for deep nets. A threshold of τ = 1.0 is the de-facto default for Transformer LLM pretraining (used by GPT, LLaMA, Mistral); a rule of thumb is that clipping should fire on roughly 5–20% of batches — much more means τ is too tight, much less means it's not protecting you. It addresses **exploding** gradients (especially the spiky loss-spike events common in RNNs and large Transformers); it does *nothing* for vanishing gradients, which require architectural fixes (residuals, normalization, better init).

**Sources**: [Gradient Clipping Techniques (ApXML LLM course)](https://apxml.com/courses/how-to-build-a-large-language-model/chapter-17-optimization-algorithms-llms/gradient-clipping-techniques) · [Gradient Clipping for Transformers (ApXML)](https://apxml.com/courses/foundations-transformers-architecture/chapter-7-implementation-details-optimization/gradient-clipping-transformers)

### 8. What causes unstable training in deep networks?
The top offenders in modern deep-network training: **(1) Vanishing/exploding gradients** — repeated multiplication through L layers with Jacobian norms ≠ 1 sends gradients to 0 or ∞; the canonical fixes are residuals, careful init (Xavier/Kaiming), and normalization (LayerNorm/RMSNorm). **(2) Attention logit explosion** — QKᵀ values can grow unbounded in deep Transformers, producing one-hot softmax outputs, zero gradient through the attention, and loss spikes; mitigated by the 1/√d scale, QK-LayerNorm, and post-attention LayerNorm. **(3) Learning-rate / batch-size mismatch** — too-high LR or too-large batch without LR warmup causes early divergence; Transformer LR schedules essentially always include a warmup phase. **(4) Mixed-precision overflow** — fp16 has max ≈ 65,504; activations or gradients beyond that become Inf/NaN. Bf16 (wider exponent) and loss scaling fix this in practice. **(5) Dead ReLUs / poor initialization** — ReLU units stuck at zero stop learning entirely; modern LLMs largely avoid this with GeLU/SiLU/SwiGLU and Kaiming-style init.

**Sources**: [Stabilizing LLM Training: Techniques and Insights (Rohan Paul)](https://www.rohan-paul.com/p/stabilizing-llm-training-techniques) · [Vanishing and Exploding Gradients (GeeksforGeeks)](https://www.geeksforgeeks.org/deep-learning/vanishing-and-exploding-gradients-problems-in-deep-learning/)

### 9. What is temperature scaling in softmax?
Temperature scaling divides logits by a scalar T before softmax: p_i = exp(z_i / T) / Σⱼ exp(z_j / T). **T < 1** sharpens the distribution (more probability mass on the top logit — at the limit T → 0 it becomes argmax/greedy). **T > 1** flattens it (more uniform — increases diversity and "creativity"). **T = 1** is the unmodified softmax. Two distinct uses: **(a) Generation control** — at inference time, T is the main knob for sampling diversity in LLMs (typically 0.7–1.0 for chat, lower for code/math, often paired with top-k or top-p truncation). **(b) Calibration** — Guo et al. (2017, *On Calibration of Modern Neural Networks*) showed modern deep nets are systematically overconfident, and learning a single scalar T on a validation set (post-hoc) dramatically improves expected calibration error while leaving predicted labels unchanged (since dividing by a positive constant preserves the argmax). It's the simplest and one of the most effective calibration methods.

**Sources**: [Temperature scaling (AWS Prescriptive Guidance)](https://docs.aws.amazon.com/prescriptive-guidance/latest/ml-quantifying-uncertainty/temp-scaling.html) · [Neural Network Calibration (Geoff Pleiss)](https://geoffpleiss.com/blog/nn_calibration.html)

### 10. Why do larger models show emergent abilities?
Wei et al. (2022, *Emergent Abilities of Large Language Models*) defined an emergent ability as one absent in smaller models but present in larger ones in a way that *cannot be predicted* by extrapolating from smaller-scale runs — citing arithmetic, multi-step reasoning, and certain BIG-Bench tasks where performance stays near-random until a parameter threshold (often 10²²–10²⁴ training FLOPs) then jumps sharply. The original intuition: at sufficient scale, the model acquires component skills (e.g., subword arithmetic primitives plus carry propagation) that all need to be present simultaneously for the task to work, producing a discontinuity. Schaeffer, Miranda & Koyejo (NeurIPS 2023, *Are Emergent Abilities of Large Language Models a Mirage?*) seriously challenged this: they showed >92% of claimed emergent abilities appear under just two metrics — **exact-string-match** and **multiple-choice-grade** — both of which are discontinuous/nonlinear in per-token error. When the *same* model outputs are re-scored with smooth metrics (token edit distance, Brier score), the apparent jumps disappear and performance scales smoothly with model size. They reproduced this in vision too, manufacturing fake "emergence" by metric choice. The honest current view: some scaling improvements are genuinely sharp, but many published "emergent abilities" are artifacts of how we measure, not phase transitions in capability — and predictability of capability gains is a live open question, not a settled one.

**Sources**: [Are Emergent Abilities of LLMs a Mirage? (Schaeffer et al., arXiv 2304.15004)](https://arxiv.org/abs/2304.15004) · [Are Emergent Abilities of LLMs a Mirage? (NeurIPS 2023 PDF)](https://papers.neurips.cc/paper_files/paper/2023/file/adc98a266f45005c403b8311ca7e8bd7-Paper-Conference.pdf)

## SQL & Data Engineering

### 1. How would you optimize a slow SQL query?
Attack in a systematic order. **First**, run `EXPLAIN (ANALYZE, BUFFERS)` to get a real execution plan with actual rows, timings, and buffer hits — never optimize from intuition. **Second**, compare *estimated vs actual rows*: a large mismatch means statistics are stale, so run `ANALYZE` (or tune `default_statistics_target`). **Third**, look for `Seq Scan` with a high `Rows Removed by Filter` — that's a missing or unusable index; add a B-tree on the filter/join columns, and if only a subset of rows is queried (e.g. `status='active'`), use a *partial index*. **Fourth**, eliminate heap fetches by promoting the plan to an *Index Only Scan* with a *covering index* (`CREATE INDEX … INCLUDE (…)`), and vacuum to keep the visibility map fresh. **Fifth**, fix join order and method (hash vs nested-loop vs merge) — usually a consequence of fixing stats, but sometimes needs rewriting correlated subqueries as joins or breaking up an N+1 issued from the ORM. **Sixth**, if `external merge Disk` appears in sorts/hashes, raise `work_mem` for that session. **Finally**, only after indexing/stats/memory are exhausted, reach for *partitioning* (range/hash) so the planner can do partition pruning on very large tables.

**Sources**: [PostgreSQL Query Optimization with EXPLAIN ANALYZE — EnterpriseDB](https://www.enterprisedb.com/blog/postgresql-query-optimization-performance-tuning-with-explain-analyze) · [The 5-Step System to Optimize Slow PostgreSQL Queries](https://medium.com/@sjksingh/the-5-step-system-to-optimize-slow-postgresql-queries-5dead7fc3cda)

### 2. Difference between OLTP and OLAP
OLTP systems run high-concurrency, short, point-lookup transactions (insert an order, debit an account) and need millisecond latency on single rows; OLAP systems scan terabytes to compute aggregates across many rows but few columns. The storage layout follows the workload: OLTP uses **row-oriented** storage (Postgres, MySQL) because fetching one row is one B-tree walk and one page read, and MVCC handles concurrent updates; OLAP uses **columnar** storage (Snowflake, BigQuery, Redshift, ClickHouse, DuckDB) where each column is stored and compressed independently, so a query reads only the columns it touches. Schemas differ too: OLTP is heavily normalized (3NF) with many narrow tables and B-tree indexes on PKs/FKs; OLAP is denormalized into star schemas with wide fact tables, few indexes, and aggressive partition/cluster pruning instead. Concurrency models diverge — OLTP optimizes for thousands of small concurrent transactions, while OLAP UPDATE/DELETE in Snowflake rewrites entire 50–500 MB micro-partitions, making it impractical for transactional workloads. The 2026 default is to run both and pipe OLTP → OLAP through CDC.

**Sources**: [OLTP vs OLAP in 2026 — ClickHouse](https://clickhouse.com/resources/engineering/oltp-vs-olap) · [Row vs Column databases — ClickHouse](https://clickhouse.com/resources/engineering/row-vs-column-database)

### 3. Explain database sharding
Sharding splits one logical dataset across many independent database nodes ("shards") so writes and storage scale horizontally. The three partitioning strategies are **range** (good for ordered scans like time-series, but prone to hot shards on the newest range), **hash** (uniform distribution but kills range scans), and **directory/lookup** (a metadata table maps keys to shards — flexible but adds a hop). The hard problem is **rebalancing**: naive `hash(key) % N` moves almost all data when N changes; **consistent hashing** places nodes and keys on a hash ring so adding/removing a node only moves the keys between adjacent ring positions, minimizing data movement. Cross-shard joins and distributed transactions are the painful trade-off — they require scatter-gather or 2PC and are usually avoided by co-locating related rows under the same shard key (Vitess "vindexes", Citus "distribution column"). Hot-shard mitigation includes salting the key, splitting the offending tablet, or "tenant pinning" so heavy tenants get isolated shards. **Vitess** (used by YouTube, Slack) sits in front of MySQL with online resharding playbooks; **Citus** does the same for PostgreSQL as a distributed-tables extension.

**Sources**: [Sharding, Rebalancing, and Consistent Hashing](https://medium.com/@profxfang/sharding-rebalancing-and-consistent-hashing-system-design-interviews-4b2b4cfe5fbd) · [5 Vitess Sharding Strategies for Live Traffic](https://medium.com/@kaushalsinh73/5-vitess-sharding-strategies-for-live-traffic-3a59e0398cd0)

### 4. What causes deadlocks and how do you prevent them?
A deadlock is a **circular wait**: txn A holds lock on row X and waits for row Y; txn B holds row Y and waits for row X — neither can proceed. PostgreSQL detects this by building a **wait-for graph** and running a cycle check every `deadlock_timeout` (default 1 second); when a cycle is found, it aborts a chosen victim with SQLSTATE **40P01 (`deadlock_detected`)**. Prevention is mostly structural: (1) acquire locks in a **consistent global order** across all code paths (e.g. always lock account with lower id first in a transfer), (2) keep transactions **short** so lock hold times shrink, (3) use the lowest viable isolation level (Read Committed instead of Serializable) to reduce lock footprint, and (4) take explicit `SELECT … FOR UPDATE` early so locks are acquired predictably rather than upgrade-promoted late. Because deadlocks are unavoidable in any system with concurrent writes, the application **must retry on 40P01** with exponential backoff and jitter — but retry is a complement to lock-order discipline, never a substitute. For application-managed mutual exclusion (e.g. cron-style singletons), prefer **advisory locks** (`pg_advisory_xact_lock`) which sidestep row-lock interactions entirely.

**Sources**: [ERROR 40P01: Deadlock detected — Bytebase](https://www.bytebase.com/reference/postgres/error/40p01-deadlock-detected/) · [PostgreSQL Deadlocks: Causes, Patterns, Fixes — Resolve.ai](https://resolve.ai/glossary/debugging-PostgreSQL-deadlock-issues)

### 5. What are materialized views?
A materialized view physically stores the result of a query on disk, so subsequent reads hit pre-computed data instead of re-running the underlying joins/aggregations — unlike a regular view, which is just a saved query text that gets rewritten and re-executed on every call. The trade-off is **freshness**: results go stale until refreshed. Refresh strategies are **on-commit** (eager, expensive), **scheduled** (cron/Airflow), or **incremental** (only changed rows reapplied). In Postgres, `REFRESH MATERIALIZED VIEW foo` rewrites the whole view and takes an `AccessExclusiveLock` blocking readers; `REFRESH MATERIALIZED VIEW CONCURRENTLY foo` does an incremental-looking swap without blocking concurrent `SELECT`s, but it **still recomputes the entire view from scratch internally** and requires at least one UNIQUE index on the matview. Native incremental view maintenance is not built in — you need the `pg_ivm` extension (not available on RDS/Aurora) for true incremental refresh. Typical use cases are pre-aggregated dashboards, leaderboards, and reporting rollups where staleness of minutes-to-hours is acceptable in exchange for sub-second queries.

**Sources**: [PostgreSQL 18 — REFRESH MATERIALIZED VIEW](https://www.postgresql.org/docs/current/sql-refreshmaterializedview.html) · [Real-Time Materialized Views with pg_ivm](https://medium.com/@sjksingh/real-time-materialized-views-with-pg-ivm-8a3f4d6cd464)

### 6. Explain the CAP theorem
Brewer's CAP theorem says a distributed data store can offer at most two of three properties — **Consistency** (every read returns the latest write), **Availability** (every request gets a non-error response), and **Partition tolerance** (the system keeps working when the network drops messages between nodes). Since real networks always partition eventually, P is non-negotiable, so the practical choice during a partition is **CP vs AP**: CP systems refuse requests on the minority side to preserve consistency (Spanner, etcd, HBase); AP systems keep serving from any node and reconcile later (Cassandra, Dynamo, Riak). **PACELC**, introduced by Daniel Abadi in 2010, is the more useful 2026 framework because it covers the much more common case where there *is no* partition: "if Partition then A vs C, **Else** Latency vs Consistency." Spanner is **PC/EC** — it pays latency (TrueTime waits, Paxos quorums) for global strong consistency; DynamoDB and Cassandra are **PA/EL** — they default to eventual consistency to keep reads sub-millisecond. The right interview answer is to drop "pick two" framing and instead ask, for any given database, what it does *during* a partition **and** what it does normally for the latency/consistency knob.

**Sources**: [PACELC design principle — Wikipedia](https://en.wikipedia.org/wiki/PACELC_design_principle) · [Beyond CAP: Why PACELC Is a Better Framework in 2026 — JavaCodeGeeks](https://www.javacodegeeks.com/2026/04/beyond-cap-why-the-pacelc-model-is-a-better-framework-for-database-decisions-in-2026.html)

### 7. Star vs snowflake schema
Both are dimensional models centered on a **fact table** (measurable events: sales, clicks) surrounded by **dimension tables** (descriptive context: product, customer, date), but they differ in how dimensions are normalized. A **star schema** keeps each dimension as a single, fully **denormalized** table — `dim_product` carries product, category, sub-category, and brand all in one row — so a typical query needs only 3–4 joins and the planner runs star-join optimizations efficiently. A **snowflake schema** normalizes those dimensions into a tree (`dim_product → dim_category → dim_dept`), which removes redundancy and saves storage but multiplies the join count, slowing reads. Star wins on query simplicity, BI-tool ergonomics (drag-and-drop SQL generators), and raw speed on columnar warehouses where dimension storage is cheap and joins are the bottleneck — which is why star is the industry default on Snowflake/BigQuery/Redshift/Databricks. Snowflake makes sense for dimensions that are **hierarchical, high-cardinality, or change frequently** (geographies, org charts, SCD type-2 history), where one source of truth matters more than a few extra joins. A common hybrid is to snowflake just those volatile dimensions while keeping the rest flat.

**Sources**: [Star Schema vs Snowflake Schema — Monte Carlo](https://montecarlo.ai/blog-star-schema-vs-snowflake-schema/) · [Star Schema vs Snowflake Schema — Built In](https://builtin.com/articles/star-schema-vs-snowflake-schema)

### 8. How would you design a data pipeline for ML systems?
A production ML pipeline is a sequence of versioned, observable stages: **ingestion** (CDC/Kafka/batch dumps into a lake) → **validation** (schema checks, drift, null/skew with Great Expectations or TFDV) → **feature engineering** (dbt for batch transforms, Flink/Spark Structured Streaming for streaming features) → **feature store** (Feast/Tecton, with an offline store for training and a low-latency online store for serving, keyed by entity) → **training set generation** (point-in-time-correct joins to avoid label leakage) → **training & eval** (tracked in MLflow with metrics, params, artifacts) → **registry & deployment** (model registry + canary/shadow rollout) → **monitoring** (latency, data drift, concept drift, prediction skew). **Orchestration** is the spine: Airflow for time-based DAGs, Dagster for asset-aware lineage and software-defined assets (Components went GA Oct 2025 with 20+ integrations), Prefect for dynamic Python-native flows. Decide **batch vs streaming per feature** — most feature stores support both — and make the same transformation code generate both offline training rows and online serving values to eliminate training/serving skew. Reproducibility comes from versioning everything: data (lakehouse snapshots, Delta/Iceberg time-travel), code (Git), features (Feast registry), and models (MLflow). A pragmatic starter stack is **Airflow + dbt + Feast + MLflow**; add Tecton/Arize only when their absence is the documented bottleneck.

**Sources**: [How to Design an ML Pipeline Architecture (2025) — datadef](https://datadef.io/guides/en/ml-pipeline-architecture) · [Feast: the Open Source Feature Store docs](https://docs.feast.dev)

### 9. Partitioning and indexing strategies
**Partitioning** physically splits one logical table into smaller children by **range** (time-series, e.g. monthly), **list** (region, tenant), or **hash** (uniform spread); the win is **partition pruning** — the planner skips irrelevant partitions when the WHERE clause filters on the partition key — and per-partition VACUUM/DROP, which makes deletes cheap. **Indexing** chooses the right access structure per column: **B-tree** is the default for equality and range on sortable data (`=, <, >, BETWEEN`, `ORDER BY`); **Hash** is faster for pure equality but rarely worth it; **GIN** is for many-keys-per-row data — `jsonb` containment, arrays, full-text `tsvector`; **GiST** for geometric/range/KNN/trigram similarity; **BRIN** stores min/max per block range and is tiny — perfect for huge, naturally-ordered tables (timestamps, sequential IDs) but useless when correlation is low. **Partial indexes** (`WHERE status='active'`) shrink hot indexes; **covering indexes** (`INCLUDE (col)`) enable index-only scans by avoiding heap visits. The cost is **write amplification** — every INSERT/UPDATE/DELETE must update every relevant index, so each extra index taxes writes and inflates WAL. Index design is therefore guided by **selectivity** (fraction of rows matched): high-selectivity columns first in composite keys, and skip indexing low-selectivity boolean flags unless paired in a partial index.

**Sources**: [PostgreSQL 18 — Index Types](https://www.postgresql.org/docs/current/indexes-types.html) · [Introduction to Indexing and Partitioning in PostgreSQL — Stormatics](https://stormatics.tech/blogs/an-introduction-to-indexing-and-partitioning-in-postgresql)

### 10. How would you process streaming data in real time?
Architect it in two layers: **a durable, replayable log** for transport — Apache Kafka (or Pulsar/Redpanda) — and **a stream-processing engine** for compute (Apache Flink, Kafka Streams, or Spark Structured Streaming). The log decouples producers from consumers, retains events for replay (key to recovery and exactly-once), and partitions by key so the processor can scale horizontally with ordered per-key delivery. **Exactly-once semantics** are achieved end-to-end by combining (a) a replayable source, (b) checkpointed/transactional state in the processor — Flink uses asynchronous distributed snapshots (Chandy-Lamport), Spark uses write-ahead logs and offset tracking — and (c) **idempotent or transactional sinks** (Kafka transactions, upsert into a DB with a dedup key). **Windowing** aggregates unbounded streams into finite chunks: **tumbling** (fixed, non-overlapping — 1-min counts), **sliding** (fixed size, sliding step — moving averages), and **session** (gap-based, per-user). **Watermarks** tell the engine "I assert no event with timestamp < T will arrive after this" so windows can close; late events past the watermark are dropped or routed to a side output. Flink is the strongest choice for low-latency, event-time-heavy, true-streaming workloads with operator-level exactly-once; Spark Structured Streaming wins when you already have a Spark/Databricks stack and tolerate micro-batch latency; Kafka Streams is best for lightweight in-JVM apps tightly coupled to one Kafka cluster.

**Sources**: [Apache Flink vs Kafka Streams vs Spark Structured Streaming — Onehouse](https://www.onehouse.ai/blog/apache-spark-structured-streaming-vs-apache-flink-vs-apache-kafka-streams-comparing-stream-processing-engines) · [Watermarking in Apache Spark Structured Streaming — Databricks](https://www.databricks.com/blog/feature-deep-dive-watermarking-apache-spark-structured-streaming)

## Python & Systems

### 1. How does Python memory management work?
CPython manages all Python objects in a **private heap** that is not directly accessible to user code; the interpreter's allocators sit between the program and the OS. For small objects (≤ **512 bytes**), CPython uses **pymalloc**, a specialized allocator with a three-level hierarchy: **arenas** (256 KiB on 32-bit, **1 MiB on 64-bit**, obtained via `mmap`), each subdivided into 64 **pools** of 4 KiB, each pool dedicated to one size class of fixed-size **blocks** (8 to 512 bytes, 8-byte aligned). Allocations larger than 512 bytes bypass pymalloc and go straight to the system `malloc` via `PyMem_RawMalloc`. Memory is freed from the program's perspective via **reference counting** and a backup cyclic GC, but CPython **does not compact** the heap, so freed blocks can leave holes; an arena is only returned to the OS when *every* pool inside it is empty, which is why long-running Python processes often appear to "leak" RSS even when Python-level objects have been released.

**Sources**: [Memory Management — Python 3.14 docs](https://docs.python.org/3/c-api/memory.html) · [Memory management in Python — Artem Golubin](https://rushter.com/blog/python-memory-managment/) · [Python allocators — memray](https://bloomberg.github.io/memray/python_allocators.html)

### 2. Explain reference counting and garbage collection
Every `PyObject` in CPython carries an `ob_refcnt` field; the macros `Py_INCREF`/`Py_DECREF` adjust it on every assignment, argument pass, and scope exit, and the object is deallocated the instant its count reaches zero — this is the **primary** memory-reclamation mechanism and is deterministic. Reference counting cannot reclaim **reference cycles** (e.g. `a.x = b; b.x = a`), so CPython runs a backup **generational cyclic GC** exposed via the `gc` module: objects are tracked in three generations (0 = young, 1, 2 = oldest); gen 0 is collected when allocations-minus-deallocations exceeds a threshold (default 700), and survivors are promoted. The collector finds cycles by computing "effective" refcounts from `gc_refs` inside the candidate set and reclaiming any subgraph with no external references. You can force a sweep with `gc.collect()`, tune thresholds with `gc.set_threshold()`, or disable the collector entirely with `gc.disable()` — common in latency-sensitive services and was famously done by Instagram to reduce copy-on-write churn under multi-process workers.

**Sources**: [gc — Garbage Collector interface (3.14)](https://docs.python.org/3/library/gc.html) · [CPython Reference Counting and GC Internals — Coding Confessions](https://blog.codingconfessions.com/p/cpython-garbage-collection-internals) · [Design of CPython's Garbage Collector — devguide](https://daobook.github.io/devguide/garbage_collector.html)

### 3. What is async programming and when should you use it?
Async programming in Python (formalized by **PEP 492**, Python 3.5+) is **cooperative concurrency**: an `async def` function becomes a coroutine that yields control at every `await` point, and a single-threaded **event loop** (`asyncio`) multiplexes thousands of such coroutines on top of OS-level non-blocking I/O (epoll/kqueue/IOCP). It is ideal when the workload is **I/O-bound and concurrency-heavy** — HTTP fan-out, database queries, websocket fan-in, scraping, LLM API calls — because while one coroutine is waiting on a socket, the loop runs others, achieving throughput that would require thousands of threads to match. It is **not** useful for CPU-bound work: a tight numerical loop never `await`s, so it blocks the entire loop and starves every other task; for that, offload to a thread/process pool via `loop.run_in_executor`. Crucially, asyncio gives concurrency but **not parallelism** by default — there is exactly one Python thread executing coroutines. Mixing blocking calls (`requests.get`, `time.sleep`, blocking DB drivers) inside async code is the most common production bug; use `asyncio.to_thread` or async-native libraries (`httpx`, `asyncpg`).

**Sources**: [PEP 492 — Coroutines with async and await syntax](https://peps.python.org/pep-0492/) · [Python's asyncio: A Hands-On Walkthrough — Real Python](https://realpython.com/async-io-python/) · [PEP 3156 — Asynchronous IO Support Rebooted](https://peps.python.org/pep-3156/)

### 4. Difference between threading, multiprocessing, and asyncio
**Threading** uses real OS threads that share one address space, so data sharing is cheap, but on the standard CPython build the **GIL** serializes Python bytecode execution — meaning threads give true overlap only when one is blocked in C-level I/O or in a GIL-releasing C extension (NumPy, hashlib, etc.); for pure-Python CPU work threading is essentially useless until you run a free-threaded 3.13t/3.14t build. **Multiprocessing** spawns separate OS processes, each with its own interpreter and GIL, giving true multi-core parallelism for CPU-bound work (image processing, ML preprocessing, numerical loops); the trade-off is that IPC is expensive (pickle/unpickle across pipes or shared memory) and per-process memory cost is much higher. **Asyncio** is a single-thread event loop optimized for high-concurrency I/O (thousands of sockets); no parallelism, no thread-safety burden inside coroutine code, but everything in the loop must be non-blocking. Decision matrix: CPU-bound → multiprocessing (or 3.13t free-threaded threading); many slow I/O calls (≥ ~100 concurrent) → asyncio; a handful of blocking I/O calls or you need to call a blocking library → threading.

**Sources**: [Faster Python: Concurrency in async/await and threading — JetBrains](https://blog.jetbrains.com/pycharm/2025/06/concurrency-in-async-await-and-threading/) · [asyncio vs threading vs multiprocessing — BSWEN](https://docs.bswen.com/blog/2026-04-14-asyncio-vs-threading-vs-multiprocessing/) · [Faster Python: Unlocking the Python GIL — JetBrains](https://blog.jetbrains.com/pycharm/2025/07/faster-python-unlocking-the-python-global-interpreter-lock/)

### 5. What causes memory leaks in Python?
Because reference counting is deterministic, "leaks" in Python are almost always **unintended retention** rather than lost pointers. The classic categories: (1) **reference cycles** that the cyclic GC cannot collect — historically these were cycles where a participant defined `__del__`, but **PEP 442** (Python 3.4+) fixed this by introducing `tp_finalize`, so finalizers no longer block cycle collection except for legacy C extensions that still use `tp_del`; (2) **unbounded caches and module-level dicts** — `@functools.lru_cache` with no `maxsize`, hand-rolled memoization, request-id → result maps in long-running services; use `WeakValueDictionary`, `cachetools.TTLCache`, or `maxsize`; (3) **closures and bound methods** holding references to large enclosing objects (a logger callback that captures `self` keeps the whole object alive for the lifetime of the listener registry); (4) **C-extension bugs** where `Py_DECREF` is missed — pure-Python tools won't see these, requiring `tracemalloc`, `objgraph`, or `memray`; (5) **dangling tasks/futures in async loops** (tasks that are created but never awaited and held in an internal set); (6) **mutable default arguments** (`def f(x=[])`) which are evaluated once at def time and accumulate forever.

**Sources**: [PEP 442 — Safe object finalization](https://peps.python.org/pep-0442/) · [Diagnosing and Fixing Memory Leaks in Python — Snyk](https://snyk.io/blog/diagnosing-and-fixing-memory-leaks-in-python/) · [Top 5 Python Memory Leak Detection Techniques — Techbuddies](https://www.techbuddies.io/2026/02/21/top-5-python-memory-leak-detection-techniques-for-long-running-services/)

### 6. Explain Python's GIL in depth
The **Global Interpreter Lock** is a mutex inside CPython that ensures only one OS thread executes Python bytecode at a time *within a single interpreter*; its existence makes CPython's reference-counting memory model trivially thread-safe (`Py_INCREF` doesn't need an atomic on every assignment) and lets C extensions assume single-threaded execution unless they explicitly release the GIL with `Py_BEGIN_ALLOW_THREADS`. The GIL is released around blocking I/O and is also periodically released so other threads get a turn — controlled by `sys.setswitchinterval()`, defaulting to **5 ms of wall-clock time** since Python 3.2 (it used to be every 100 bytecodes). Two major escape hatches have landed: **PEP 684 — per-interpreter GIL (Python 3.12)** gives each subinterpreter its own GIL so multiple subinterpreters in one process run in parallel, and **PEP 703 — free-threaded CPython** ships as an opt-in build in 3.13 (October 2024, experimental) and in 3.14 (October 2025) it advances out of experimental per **PEP 779**, becoming an officially supported but non-default build. Single-threaded overhead of the free-threaded build dropped from ~40% in 3.13t to roughly **5–10%** in 3.14t, and most major C extensions (NumPy, PyTorch, Pandas) now ship free-threaded wheels.

**Sources**: [PEP 703 — Making the GIL Optional in CPython](https://peps.python.org/pep-0703/) · [PEP 684 — A Per-Interpreter GIL](https://peps.python.org/pep-0684/) · [PEP 779 — Criteria for supported status for free-threaded Python](https://peps.python.org/pep-0779/) · [Thread states and the GIL — Python 3.14 docs](https://docs.python.org/3/c-api/threads.html)

### 7. How would you profile Python code performance?
The cardinal rule is **measure first, optimize second** — and measure the right thing: wall time, CPU time, memory, or syscalls each need a different tool. Start with **cProfile** (stdlib, deterministic, function-level) to get total/cumulative time per call and visualize the resulting `.prof` with **SnakeViz** (browser sunburst/icicle of the call graph); cProfile has measurable overhead so don't trust microbenchmarks. Once you've localized a hot function, drop in **line_profiler** (`@profile` + `kernprof -l -v`) for line-by-line timings — this is where you see which line in the hot function is the actual culprit. For **production** or running processes, use **py-spy** (sampling, no instrumentation, attaches to a live PID, generates flamegraphs with `py-spy record`) — safe to run against prod. **Scalene** is the modern all-rounder: low-overhead sampling that separates Python vs native time, includes CPU+GPU+memory, and gives line-level memory deltas. For memory specifically use **tracemalloc** (stdlib, snapshot-and-diff to find which line allocated growing memory) or **memray** (Bloomberg's tool, better for large heaps). For system-level — syscalls, off-CPU time, GIL contention — use Linux `perf` and the eBPF-based profilers.

**Sources**: [SnakeViz documentation](https://jiffyclub.github.io/snakeviz/) · [A Comprehensive Guide to Profiling in Python — Better Stack](https://betterstack.com/community/guides/scaling-python/profiling-in-python/) · [8 Python Profiling Tools That Find Real Hot Paths](https://medium.com/@bhagyarana80/8-python-profiling-tools-that-find-real-hot-paths-4d4ae57fecd3)

### 8. What are metaclasses?
A metaclass is **the class of a class**: where instances are made by calling a class, classes themselves are made by calling a metaclass, and by default that metaclass is `type`. When Python encounters `class Foo(Base, metaclass=Meta): body`, it executes the body to build a namespace dict, then calls `Meta('Foo', (Base,), namespace)`, which returns the class object — so `Meta.__init__` and `Meta.__new__` are the hooks that intercept class creation. The canonical use case is framework authoring: Django's `ModelBase` metaclass walks the namespace at class-construction time, finds every attribute that is a `Field` instance (calling its `contribute_to_class`), registers the model with the ORM, and builds the `_meta` options object — all so the user can just write `name = models.CharField(...)`. Other legitimate uses: enforcing API contracts (abstract base classes — `ABCMeta` uses this mechanism), automatic registration of plugins, and sealing/finalizing classes. As **Tim Peters** put it: *"Metaclasses are deeper magic than 99% of users should ever worry about. If you wonder whether you need them, you don't."* In modern Python, `__init_subclass__` and class decorators replace metaclasses for ~80% of the cases people used to reach for them.

**Sources**: [Contributing to classiness in Django — James Bennett](https://www.b-list.org/weblog/2019/mar/04/class/) · [How Django's ModelBase metaclass transforms class definitions — Ameer Hamza](https://ameerhamza1.medium.com/how-djangos-modelbase-metaclass-transforms-class-definitions-into-model-instances-during-import-5591ad5b76ec) · [The Secret Life of Python: Metaclasses](https://dev.to/aaron_rose_0787cc8b4775a0/the-secret-life-of-python-metaclasses-classes-that-make-classes-3lag)

### 9. How do decorators work internally?
`@decorator` above a `def func` is purely syntactic sugar for `func = decorator(func)` — the decorator is a callable that receives the function object and returns *something* (usually but not necessarily another callable) that is rebound to the original name. Because the wrapper replaces the original, attributes like `__name__`, `__doc__`, `__qualname__`, `__module__`, and `__wrapped__` get clobbered; **`functools.wraps`** (itself implemented via `functools.update_wrapper` + `partial`) copies those attributes from the wrapped object to the wrapper so introspection, debuggers, and Sphinx still work, and also sets `__wrapped__` so `inspect.signature` can dig through layers. **Parameterized decorators** (`@retry(times=3)`) add one outer layer: `retry(times=3)` runs first and returns the actual decorator, which is then applied — so it's a function that returns a function that returns a function. **Class-based decorators** implement `__call__` so the instance is callable, and store state on `self` instead of in a closure — but plain class wrappers break on methods because the wrapping instance isn't a descriptor (no `__get__`), so `instance.method` doesn't bind `self`; the fix is to implement `__get__` (the **descriptor protocol**) returning a bound version, which is exactly what Graham Dumpleton's `wrapt` library exists to handle correctly across functions, methods, classmethods, and staticmethods.

**Sources**: [Primer on Python Decorators — Real Python](https://realpython.com/primer-on-python-decorators/) · [Peeking into the internals of functools.wraps — Redowan's Reflections](https://rednafi.com/python/internals-of-functools-wraps/) · [The interaction between decorators and descriptors — Graham Dumpleton](http://blog.dscpl.com.au/2014/01/the-interaction-between-decorators-and.html)

### 10. How would you build a scalable Python backend for AI inference?
Treat the **API tier** and the **model tier** as separate scaling axes. The API tier is a stateless **async framework** — FastAPI/Starlette or LiteStar on Uvicorn — that does auth, validation, rate-limiting, prompt assembly, and streaming responses; because every call is I/O-bound (network → inference server → network), async lets one Python process hold thousands of in-flight requests. **Never run the model in-process** with the API: load it inside a dedicated **inference server** — **vLLM** (PagedAttention + continuous batching, the de-facto OSS standard for LLMs), **NVIDIA Triton** with the vLLM/TensorRT-LLM backend (dynamic batching, multi-model, multi-framework), or HuggingFace **TGI** — so GPU pods scale independently of CPU pods and you get **continuous in-flight batching** for free, which is what makes throughput economical. Put a **queue or stream broker** (Redis/RabbitMQ for short tasks, Kafka for high-throughput async pipelines, Celery/Arq/Dramatiq for Python-native job orchestration) between API and workers to absorb spikes and give back-pressure when GPUs are saturated, so requests degrade gracefully instead of OOM-crashing. **Horizontal scaling** is two HPAs: API pods scale on CPU/RPS, GPU pods scale on a custom metric like queue depth or KV-cache utilization, with **separate worker processes per queue** (don't multiplex CPU jobs and GPU jobs onto the same pool — they have incompatible failure modes and timeouts). Add **observability** end-to-end: OpenTelemetry traces from API → queue → inference, Prometheus metrics for per-stage latency, token throughput, GPU utilization, batch fill ratio, and cost-per-request — without these you cannot tell whether scale problems are model-bound, queue-bound, or API-bound.

**Sources**: [Serving LLMs with vLLM + FastAPI at Scale — dasroot](https://dasroot.net/posts/2026/03/serving-llms-vllm-fastapi-scale/) · [vLLM Backend — NVIDIA Triton Inference Server](https://docs.nvidia.com/deeplearning/triton-inference-server/user-guide/docs/vllm_backend/README.html) · [AI Model Serving Architecture — RunPod](https://www.runpod.io/articles/guides/ai-model-serving-architecture-building-scalable-inference-apis-for-production-applications) · [Scalable and Secure AI Inference in Healthcare (FastAPI vs Triton)](https://arxiv.org/html/2602.00053v1)
